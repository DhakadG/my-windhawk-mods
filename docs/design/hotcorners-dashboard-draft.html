Win-X Hot Corners 4.1.4 · UI draft for review

Two surfaces, one job each

The Windhawk settings page becomes where you configure. The dashboard becomes where you see. This is the draft of the second one — agree it before any of it gets built.

The dashboard already exists and already draws a screen diagram — ZoneRectInDiagram() lays out all twelve zones today. What it doesn't have is a way to tell you which display you're looking at without reading a dropdown, and it carries the full configuration burden because the settings page was retired in 4.1.0.

Windhawk v2 removes the reason that retirement happened: settings now render as collapsible groups, so forty settings in a flat list is no longer the only option. That frees the dashboard to stop being a form.

The proposal

What changed, and why

ElementTodayProposedReason
Display picker Combo box (IDC_MONITOR) Tab strip, one tab per display A dropdown hides how many configurations exist. Tabs make the set visible and make "these settings are for this display" unambiguous — which was the actual request.
Configuration count Not shown Badge on each tab Answers "have I set anything up on the second screen?" without clicking through.
Disconnected display Listed the same as any other Dimmed dot, tab still selectable A saved configuration for an unplugged monitor is not an error, but it shouldn't look live.
Screen box Fixed proportions Derived from reported resolution A portrait or ultrawide display should look like one. Falls straight out of the existing rect math.
Zone labels Action combo per zone Action name in the zone The map becomes readable at a glance instead of being a form laid out in a square.
Zone detail Action only Action, arguments, and every timing value in effect — each marked global or overridden A zone inherits five numbers it never shows you. "Why did this one fire late?" was unanswerable without reading the settings store by hand.
Long action names Overflowed the zone Clamped in the block, spelled out in the detail row A corner block is square and small; "Switch to Last Window" never fits. Side strips get vertical text, which is the only way "Notification Centre" sits inside one.
Editing In the dashboard In Windhawk settings One place to change things. The dashboard stops being a second source of truth — which is what caused the v4.1.4 index bug.

The two open questions

1. How should an alternate-action zone read?

Recommendation: primary action plus a ⇄ badge; both actions in the detail row. Alt+S | Alt+H will not fit in a corner block at any realistic window size, and truncating it produces a label that is actively misleading. The badge says "there are two here" honestly, and the detail row below the diagram has the space to spell them out. Bottom-centre in the mock shows this.

2. Real monitor arrangement, or one screen at a time?

Recommendation: one screen at a time. An arrangement view has to shrink every screen to fit the widest span, and on three displays the corner blocks become too small to label — the diagram stops doing the one job it has. The tabs already answer "which display", so the arrangement view would be spending most of the window to repeat what the tab strip says. If locating a display is ever a real problem, the cheaper fix is the identify-on-screen overlay Windows itself uses, not a permanent mini-map.

Is it buildable in Win32?

Everything here is drawn, not composed from controls, which is why it stays cheap. The mod already owns the paint path.

PieceImplementation
Tab stripSysTabControl32 with TCS_OWNERDRAWFIXED, or owner-drawn buttons. The existing palette already themes it; the accent underline is one FillRect.
Screen box + zonesZoneRectInDiagram(), unchanged. Hit-testing is PtInRect over the same rects it already returns.
Zone labelsDrawTextW with DT_CENTER | DT_WORDBREAK | DT_END_ELLIPSIS inside the zone rect.
HoverWM_MOUSEMOVE + TrackMouseEvent for WM_MOUSELEAVE; invalidate only the two affected rects.
Detail rowStatic text, repainted on selection change.
Aspect ratioMonitorInfo::rcMonitor is already captured per display.
Watch for

The centre zones sit inside the edge strips. The current code already splits each edge into two segments around its centre block, and the comment above ZoneRectInDiagram records why — they used to overlap, so hovering a centre highlighted the whole edge. Any redraw work must preserve that split, including the secondHalf parameter, or the bug comes back.

Every setting key stays exactly as it is. Nobody's configuration resets because the UI was rearranged.

Verdict on the dashboard

Keep itkeep — but read-only in the first pass. It is the only thing in the mod that answers "what is set up where" in one look, and no list of forty settings will ever do that.

Drop the editing controlscut — the zone action combos, the numeric fields, Save and Reset. Two surfaces that both write the same store is exactly the shape that produced the 4.1.3 and 4.1.4 bugs, where the dashboard addressed configurations by list position and wrote over the wrong one.

If read-only turns out to be annoying in daily use, clicking a zone can deep-link into the Windhawk settings page later. That's an addition to a working thing, not a thing to design now.

Before anything gets built

  • Confirm the tab strip over the dropdown, and read-only over editable — those two decisions shape everything else.
